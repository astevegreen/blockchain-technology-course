Micro-Lab: Reading a Contract With No Source

Selectors, signature lookups and decompiled code, as an analyst reads them. Goes with lesson 11-FO (day 8). Everything runs in this page; nothing is sent anywhere.

Questions you answer

You are asked what an unverified contract at 0xc0de…7e57 does. Its source was never published, so you have its decompiled code, two of its transactions and three of its storage slots. Answer these for that contract (the problem below):

  1. For each function: what is its selector, and what name does a signature lookup give it?
  2. What does each function let its caller do, and who may call it?
  3. What did transactions P1 and P2 actually do? Use their logs.
  4. Does each looked-up name match what the code does?
  5. For each function, write one sentence an agent could read, with a confidence word from the course scale (11-FO, "How sure"), and say what the sentence rests on.

Work through the worked example first. The contracts, addresses and transactions on this page are made up for the lab; the selectors are real Keccak-256 values, computed by the page.

Two tools

Selector checker

A selector is the first four bytes of the Keccak-256 hash of the function's signature: its name and argument types, with no spaces and no argument names [solidityteam_abispecification_2026].

Try transfer(address,uint128), then transfer(address to, uint256 amount).

Calldata reader

A call's input data is the selector, then the arguments in 32-byte words. "The encoding is not self describing": you need the function's types to read the words [solidityteam_abispecification_2026].

The signature list the reader uses

A signature database maps selectors back to signatures that people have submitted [fourbyte_signaturedatabase_2026]. This page carries a small list of its own for the lab. A match gives a name, not proof of what the code does, and two signatures can share a selector [foundry_functionselectorcollision_2026].

Worked example: a verified token

Transaction W1 calls the token contract 0x5afe…0001. A verifier reports an exact match for it: the published source compiles to the same bytecode, byte for byte [sourcify_exactmatch_2026].

  1. Read the selector. Pick W1 in the calldata reader. The input starts a9059cbb.
  2. Look it up. The list gives transfer(address,uint256). Check it in the selector checker: the hash of that signature starts a9059cbb.
  3. Read the arguments with those types. Word 0 is an address, 0xbeef…; word 1 is 1,500.
  4. Check the logs. W1 logged Transfer(from 0xdad…, to 0xbeef…, 1500). EIP-20 requires a token to log Transfer when tokens are transferred [vogelsteller_eip20tokenstandard_2015]. The code, the name and the effect agree.

Now compare what a decompiler would print from the bytecode with the verified source. The decompiled column is illustrative, written for this lab in the style decompilers print, not a real tool's output.

Verified source 
/// @notice Move tokens from the caller to another address.
function transfer(address to, uint256 amount)
    public returns (bool)
{
    require(balanceOf[msg.sender] >= amount);
    balanceOf[msg.sender] -= amount;
    balanceOf[to] += amount;
    emit Transfer(msg.sender, to, amount);
    return true;
}
Decompiled from the bytecode (illustrative) 
function Unresolved_a9059cbb(address arg0,
                             uint256 arg1)
    public returns (bool)
{
    require(storage_map_a[msg.sender] >= arg1);
    storage_map_a[msg.sender] -= arg1;
    storage_map_a[arg0] += arg1;
    emit Transfer(msg.sender, arg0, arg1);
    return true;
}

A decompiler rebuilds structure, not intent: names, comments and purpose were never in the bytecode, and types are inferred [grech_elipmocadvanceddecompilation_2022]. Put each item in a column of 11-FO's decompiler table.

Problem: an unverified contract

The contract at 0xc0de…7e57 has no match on a verifier. Below is its decompiled code (illustrative, written for this lab in the style decompilers print; for a real contract you would run an open-source decompiler such as heimdall-rs [becker_heimdallrs_2026]), the values of three storage slots read from a node, and two transactions. Answer the questions at the top.

// Illustrative, not a real tool's output
function Unresolved_a9059cbb(address arg0, uint256 arg1) public returns (bool) {
    require(storage_map_a[msg.sender] >= arg1);
    uint256 var_a = arg1 * storage[3] / 100;
    storage_map_a[msg.sender] -= arg1;
    storage_map_a[arg0] += arg1 - var_a;
    storage_map_a[storage[2]] += var_a;
    emit Transfer(msg.sender, arg0, arg1 - var_a);
    emit Transfer(msg.sender, storage[2], var_a);
    return true;
}

function Unresolved_42966c68(uint256 arg0) public {
    require(msg.sender == storage[1]);
    storage[0] += arg0;
    storage_map_a[storage[1]] += arg0;
    emit Transfer(address(0), storage[1], arg0);
}

Optional challenge

  1. Selector 42966c68 has two signatures on file. Pick P1 in the calldata reader and read its argument both ways. Which signature do you report, and why? (In a correct encoding, a bytes16 value sits at the start of its word and the rest of the word is zero [solidityteam_abispecification_2026].)
  2. Bob sent 250 in P2. Explain to an agent, in two sentences, why 0xcafe… received 245 and where the other 5 went. Which storage slot sets the share?
  3. Type burn(uint256) and collate_propagate_storage(bytes16) into the selector checker. What does that tell you about trusting a lookup?
