Day 8 lab: a cross-chain trace

This lab reads a frozen snapshot of real transactions from two thefts that crossed chains. North Korea stole about $1.5 billion from the exchange Bybit on or about 21 Feb 2025 [1]; some of it was converted to Bitcoin [1] [2]. On 18 Apr 2026 (UTC, query 10), a forged bridge message released 116,500 rsETH from Kelp DAO's bridge, about $292 million [3] [4].

Every query is written for you. On the query page, press "Run" under a query, then read its output. You never edit the SQL. Write your answers down as short notes, and draw the diagram on paper. Your instructor checks them with you; worksheet question 17 is the day's graded point.

The snapshot is frozen: every run gives the same answer. Query 16 says how far each chain was read: write "as of" with its block, not "now". If the query page will not load, use the saved results: they show every query's output, so every question has the same answer there.

Where to start

  • Everyone starts with Name the money and the flaw: the prediction lab and the Find the line game on the course chain. Your instructor walks this with you.
  • Then the contract read (questions 1 to 4): the contract Bybit's wallet was tricked into running.
  • Most students then do the worked example, Bybit's ETH to Bitcoin (questions 5 to 10). It shows you how to follow money through a swap that crosses chains.
  • If your pretest showed you can already follow a swap across chains, you may skip the rest of the worked example, but everyone does its Across the bridge steps (about 20 minutes): they are the only place the lab shows how to follow money across a bridge. Then go to the problem, Kelp DAO (questions 11 to 16).
  • Everyone does the graded note (worksheet question 17). The challenge at the end is optional.

Reading contracts and bridges

  • A call to a contract starts with a 4-byte selector: the first four bytes of the Keccak-256 hash of the function's signature, such as transfer(address,uint256) [7]. The call data does not carry the name.
  • 4byte.directory maps selectors back to names that people have submitted [8]. Two different signatures can share a selector [9], so a name from a selector is a claim, not a fact.
  • A delegatecall runs another contract's code inside the caller's own account: the code works on the caller's storage and balance [10]. A Safe multisig wallet is a proxy: it keeps the address of its logic contract (its "master copy") in storage and delegatecalls into it [6] [10].
  • THORChain is a cross-chain exchange: anyone can swap a coin on one chain for a coin on another [11]. The worked example's Across the bridge steps show how to follow money through it.
  • A LayerZero bridge sends messages between chains. Each message has an ID (guid). A channel is one sending contract on one chain talking to one receiving contract on another, and it numbers its messages 1, 2, 3 with no gaps (the nonce); a message is executed only once every earlier number on its channel has been verified [14]. Queries 9 and 12 read both.
  • Times are UTC. Amounts are exact, in the asset's own units.

How you answer

Some answers are facts the chain records: an address, an amount, a block. A fact takes no confidence word. Others are judgments about what the facts mean. Give each judgment a confidence word [13]:

HighTwo or more independent lines of evidence agree, and no known failure of the reasoning applies.
ModerateOne strong line of evidence, or weaker lines that agree, but a known false positive could apply.
LowTiming, amount or behavior alone, or one unverified label such as an explorer tag.

Independent means a different kind of evidence, not a second look at the same transaction.

The code

Two pieces of code decide what the transaction at 14:13:35 did. Read them line by line, then check what you read against the chain.

The wallet. Bybit's cold wallet is a Safe proxy: it keeps the address of its master copy in storage slot 0 and delegatecalls every call into it [6]. Below is Safe's proxy code as published in release 1.1.1 [15], the release of the master copy 0x34cfac64… the wallet ran [16]. Lines left out are marked ….

contract Proxy {

    // masterCopy always needs to be first declared variable, to ensure that it is at the same location in the contracts to which calls are delegated.
    // To reduce deployment costs this variable is internal and needs to be retrieved via `getStorageAt`
    address internal masterCopy;
    …
    function ()
        external
        payable
    {
        …
            let masterCopy := and(sload(0), 0xffffffffffffffffffffffffffffffffffffffff)
            …
            let success := delegatecall(gas, masterCopy, 0, calldatasize(), 0, 0)
            …
    }
}

The contract it was tricked into running. NCC Group read 0x96221423… from its bytecode: they put it through Etherscan's decompiler and printed the result [6]. As in day 8's lesson on bytecode, the decompiler's output is a reading of the bytecode, not the attacker's source.

def storage:
  stor0 is uint256 at storage 0
def _fallback() payable: # default function
  revert
def transfer(address _to, uint256 _value) payable:
  require calldata.size - 4 >= 64
  require _to == _to
  stor0 = _to

The decompiler wrote the names. transfer rests on the selector you looked up in question 1; the body is what the bytecode does.

Who could make the wallet run it. The wallet called 0x96221423… with a delegatecall, through its own execTransaction, which runs only what the wallet's required signers sign [6].

Now check the code against the chain. In query 1, path 0 is the wallet running its old master copy (0x34cfac64…, selector 0x6a761202, execTransaction on 4byte [8]), and path 0_0 is the delegatecall into 0x96221423…. Every later call runs 0xbdd077f6…. The code you read and the change you see on the chain are two different kinds of evidence.

Worked example: Bybit's ETH to Bitcoin (21 to 26 Feb 2025)

This follows the stolen ETH from the wallet, through a hub, into THORChain, and out on Bitcoin. Elliptic reports that the stolen tokens, such as stETH and cmETH, were swapped for ETH on exchanges with no one to freeze them, and that most of the ETH became Bitcoin [2].

Find it

  1. Open the query page and wait for "Ready". Run query 2. Five sweeps, 14:15:11 to 14:16:11, move USDT, cmETH, stETH, mETH and 401,346.77 ETH (transaction 0xb61413c4…) to 0x47666fab8bd0ac7003bce3f5c3585383f09486e2.
  2. Run query 3. At 15:48, four transactions each send 10,000 ETH to a new address. The FBI lists one of them, 0x51e9d833…, among the addresses the thieves used [1].

Follow the money

  1. Run query 4. Three days later, 0x31c4b3da… collects ETH from all four: 929.21 from 0x51e9…, 713.81 from 0xcd1a…, 304.52 from 0x1eb2… and 98.99 from 0x83ef…, plus two senders this snapshot does not trace. That is a hub.
  2. The hub also got 17 payments of 0.000001 ETH or less. Run query 5: 16 of the senders match the first four and last four characters of an address the hub had paid, and each arrives 5 to 207 blocks after that payment. That is address poisoning: a look-alike sends a tiny amount, hoping the victim copies the wrong address from their history next time [12]. The poisoner is a stranger fishing, not the thief's own wallet: leave the look-alikes out of the cluster.

Across the bridge (everyone, about 20 minutes)

The agent has followed the thieves' ETH to the hub. From there, three payments of 9.98 ETH, from three fresh addresses, go into THORChain. "Is the money gone? Or can we see where it went?"

Predict first, before you run query 6, and write your answer down. Three fresh addresses each send 9.98 ETH into THORChain on Ethereum, in the same second. What can the record tell you about where that money went?
(a) Nothing: the bridge holds it now, and the trail ends there.
(b) Only a guess: look on other chains for arrivals worth about the same, soon after.
(c) The deposit itself says which chain, which coin and which address to pay, and the payout on the far chain names the deposit it answers.
(d) Only the bridge's own website can say.
Then say how sure you are: High, Moderate or Low.

  1. Read the deposit. Run query 6. At 21:56:47 on 25 Feb, three fresh addresses each deposit 9.98 ETH into THORChain's vault 0x863df8de…. The deposit's "to" is THORChain's, but who gets paid is written inside it. Take the first deposit, 0xe62e6205…, and read its memo field by field, split at each colon: = means swap; BTC.BTC is the coin wanted, bitcoin on Bitcoin; bc1qjm4u92xpcahtmhtjrp3r4vdy6reg4yg4lvz79z is the address to pay [17]. On Ethereum the memo is a text argument of THORChain's router call [18]. Leave the last field, 0/10/0, aside: it sets limits on the swap [17]. Query 6 shows the second and third fields as asks_for and pay_to; do the other two deposits ask for the same?
  2. Read the payout. Run query 7. Forty-three minutes later THORChain's Bitcoin vault pays 0.27748623, 0.27393619 and 0.27305932 BTC to that address. Each payout carries its own memo, OUT: and the hash of the deposit it answers [19]; query 7 pairs them on that hash, and as_the_memo_asked is true when the payout went where the deposit asked. Two records, on two chains, that point at each other.
  3. Now try the guess. Run SQL query 17: every payout that address received from 22:00 to 23:30. Look only at paid_utc, minutes_after_deposits and btc, and cover the last two columns. Say you had only amount and time. Which payouts fall within 30 minutes of the deposits? Within an hour? Which three would you pick? Now read memo and answers_deposit. How many of your picks were the deposits' payouts? The three deposits are the same amount in the same second, and ETH went in while BTC came out, so the amounts compare only through a price. Research on bridges finds the same: a wider window adds wrong matches, and amount and time alone often pick wrong [20] [21].
  4. Name it: the memo. The memo is the instruction a deposit gives the bridge: the action, the coin wanted and the address to pay (SWAP:ASSET:DESTADDR:…) [17]. The payout's own memo, OUT: with the deposit's hash, points back [19]. A bridge must know where to pay before it can pay, so the deposit carries that, and the analyst reads it to learn where the money was sent.
  5. The bridge's own explorer. The second way is the bridge's own site: paste a hash, read the status, and take the far side's hash. Day 8's slide "A bridge's explorer pairs send and arrival" shows one Kelp send on LayerZero Scan [22]; on THORChain, the node's API gives an inbound hash's status [23]. You do not open them in this lab. They are the bridge's account of itself, so the two chains stay the check.
  6. A twist. THORChain's developers have proposed dropping the payout memo (issue 2232, open since 31 Jul 2025, as of 10 Nov 2026) [19]. Say a later case's payouts carry no OUT: memo. What links a deposit to its payout now? Nothing, the trail ends; the deposit's memo still names the coin and the address, so bitcoin arriving there soon after is a lead, said at Low confidence; the bridge's explorer, which settles it; or the closest amount? Use SQL query 17 to say how strong that lead would be on this evening.
  7. Say it. The agent asks where the three deposits went. Write one or two sentences: when and what went in, where each memo asked to be paid, what was paid and when, your confidence and why. Add what amount and time alone would have done here.

Three ways across a bridge, in the order to trust them: the record the deposit and the payout carry (a memo, or a message ID); the bridge's own explorer; amount and time, which is a check, and on its own a Low-confidence lead.

The rest of the trail

  1. Run query 8. As of Bitcoin block 972,854, bc1qjm4u… took in and sent out 61.785 BTC over two days, and holds nothing.

What you report

  • The ETH crossed to Bitcoin through THORChain: three deposits from Ethereum on 25 Feb 2025 at 21:56:47, paid out on Bitcoin to bc1qjm4u… at 22:39:21. High: the deposit memos and the payouts are two records on two chains, and they agree. The address took eight other payouts that evening; amount and time alone would have picked wrong ones.
  • The hub 0x31c4b3da… pooled the thieves' ETH. Moderate: it collects from the four addresses the wallet's ETH went to, one of them on the FBI's list; the hub itself is on no list here.
  • The diagram: cold wallet 0x1db92e2e… → (ETH and tokens) 0x47666fab… → (4 × 10,000 ETH) four addresses → (ETH) hub 0x31c4b3da… → … → (9.98 ETH × 3) THORChain vault 0x863df8de… on Ethereum → (BTC × 3) bc1qjm4u… on Bitcoin.
  • The chain does not show who holds the keys. This snapshot does not show what became of the hub's ETH beyond these deposits: that is on Ethereum's chain, but the snapshot holds only the case's transactions.

The problem: Kelp DAO's rsETH, Unichain to Arbitrum (18 to 21 Apr 2026)

The pattern is a bridge, not a swap: the money is released on one chain because of a message said to come from another. Each question has a hint under it.

  1. Query 9. Which message number did the delivery on Ethereum claim to come from, and how many had the Unichain contract sent? What does that tell you?

    The message. Each number on a channel stands for one message the sending contract sent [14]. Compare the number the delivery claimed with the number the sending contract had reached, on both chains, at the same time.

  2. Query 10. How much rsETH was released, to whom, and where did it go in the next six minutes?
  3. Query 11. What did 0x1f4c1c2e… do with its rsETH, what did it get back, and where did that go? Which contracts did it deal with? What can you say about who runs them?

    Names from tokens. In query 11 the contracts are named only by the tokens they mint, such as aEthrsETH and variableDebtEthWETH. A token name is a claim made by whoever deployed it, like a name from a selector. Blockaid reports that the attacker put the rsETH into Aave V3 as collateral and borrowed WETH against it [3]. Say what the tokens show, what the source adds, and how much rsETH the snapshot shows going in.

  4. Query 12. Which addresses sent rsETH across the bridge, to which chain, to which address there, and how long did each take? What happened to the one message sent back?

    The far side. Compare each send's receiver with its sender. Cross the bridge as in Across the bridge: the record first (here the message ID, guid, plays the memo's part), then the bridge's explorer, then amount and time as a check.

  5. Queries 13 and 14. What reached the collecting address on Arbitrum, and what moved it out? Did the collecting address's owner sign that move?

    What the snapshot does not hold. rsETH crosses to Arbitrum; ETH arrives at the collecting address. Say which step you cannot see. That step happened on Arbitrum's chain: it is missing from this snapshot, which holds only the case's transactions, not from the chain.

    The freeze. Arbitrum's Security Council says it moved the ETH with a cross-chain transaction made as if it came from the collecting address [5]. Compare its figure with query 13. from_address shows whose account a transaction acts for, not always who signed it.

  6. Queries 14 and 15. Where is that ETH as of the snapshot? What can you say about the address that holds it?

    The holder. The address that holds the ETH as of the snapshot has no label. The Council says releasing the ETH is for Arbitrum's governance to decide [5]. Say what the chain shows, and stop there.
