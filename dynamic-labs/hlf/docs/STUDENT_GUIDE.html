Hyperledger Fabric Lab — Westview Used-Car Exchange (Student Guide)

This lab gives you a hands-on, web-based Hyperledger Fabric sandbox. You will interact with a private permissioned blockchain using a browser UI that includes:

  • a CLI terminal (for commands)
  • live network logs
  • live block creation
  • live ledger state changes

Learning Goals (60–90 min)

By the end of this lab, you will be able to:

  • explain how permissioned blockchains differ from public ones
  • describe Fabric’s peers, orderer, MSP, channels, and chaincode
  • submit multiple transactions and observe endorsement → ordering → commit
  • query, create, transfer, update, and remove ledger entries representing real-world inventory
  • articulate why a private network can reduce disputes in multi-party workflows (e.g., titles, wholesale swaps, pricing changes)

This lab aligns with the module that precedes it (distributed ledgers + Hyperledger Fabric) and complements your other course labs focused on consensus attacks, smart contract risks, and protocol vulnerabilities.

Lab Narrative: Operation Westview Wheels

Welcome to Westview, New Jersey—a charming town with excellent pizza, suspiciously dense traffic circles, and an unusually high concentration of used-car dealerships.

The dealerships have formed a private, permissioned network called the Westview Used-Car Exchange (WUCE). The pitch was simple:

  • Every dealer wants to move inventory quickly.
  • Nobody wants to fight about who listed what, when the price changed, or whether a car was “already sold” (again).
  • The state title system is reliable except when it isn’t, and the “backup process” involves a fax machine that sounds like a dying robot.

Two dealerships are key participants in today’s exercise:

  • Org1 = Cascadia State University (the institution that issues and records diplomas)
  • Org2 = Chesapeake Canoe University (an employer that verifies credentials on the shared ledger)

Your job is to operate the exchange as a shared system of record:

  1. bring the network online,
  2. initialize the shared inventory ledger,
  3. run several common dealership workflows (listings, wholesale swaps, price updates, and removals),
  4. observe how Fabric enforces trust between competing organizations.

How cars map to ledger assets (important):

  • ID = a short inventory ID (think “stock number”)
  • Color = exterior color
  • Size = mileage bucket (integer; interpret as mileage in tens of thousands, e.g., 6 ≈ 60,000 miles)
  • Owner = who currently controls the listing (dealership or buyer)
  • AppraisedValue = listed price in USD

Canonical vs optional fields:

  • Canonical fields (always present): ID, Color, Size, Owner, AppraisedValue (and docType if shown).
  • Optional car fields (may appear): Year, Make, Model, Trim, Mileage, VIN.
  • If Mileage is provided, then Size ~= floor(Mileage / 10000) (the chaincode updates Size when you set Mileage).

Interface Overview

The web UI provides four terminals:

Terminal Purpose What You’ll Observe
CLI Run commands Command output + errors
Logs Network activity Endorsement, ordering, commits
Blocks Block creation New block height updates
State Ledger changes Asset state changes

Buttons you will use:

  • Start Network — launches the Fabric network and chaincode
  • Stop Network — shuts it down cleanly
  • Student Guide — opens this document in a separate window

1) Start the Network (5 min)

  1. Click Start Network.
  2. Watch the Logs terminal for startup progress.
  3. Wait until status shows Network Running.

Why this matters: Fabric is not “always on.” Operators control network lifecycle and membership. This is a key difference from public blockchains.

2) Confirm the Channel Is Live (5 min)

In the CLI terminal, run:

peer channel getinfo -c mychannel

Expected: a response that includes height: N.

Why this matters: Channels are private subnets in Fabric. This confirms your peer is connected and the channel ledger exists.

3) Initialize the Ledger (10 min)

In the CLI terminal, run:

invoke init-ledger

Watch all four terminals:

  • Logs: endorsement + commit activity
  • Blocks: new block created
  • State: initial assets appear

Why this matters: This is the full Fabric transaction lifecycle.

What’s happening in this scenario: init-ledger pre-loads the exchange with a starter inventory so you can immediately practice the end-to-end workflow.

4) Inspect the Exchange Inventory (5–10 min)

Query the full vehicle list (all listings on the exchange):

query all

Optional: pretty‑print with jq:

query all | jq

You should see a JSON list of “assets.” In this lab, each asset represents a used car listing.

Why this matters: Reads do not create blocks, which makes Fabric efficient for queries. The ledger state is still cryptographically verifiable, even when you’re “just reading.”

5) Transaction Run Checklist (20–30 min)

Complete the checklist in order. This ensures you log 8–12+ total transactions and verify each step with a query. Use the invoke helper for write actions and the query helper for reads.

Step 1 — Initialize the ledger:

invoke init-ledger

Step 2 — Verify starter inventory:

query all

Step 3 — Create two new listings:

invoke create car900 silver 6 carmaste 14995
invoke create car901 blue 12 not-your-fathers 9995

Step 4 — Verify with a query:

query all

Step 5 — Add vehicle details to one listing:

invoke set-vehicle car900 2019 Toyoda Coroll-Yeah SE 45888 WV-F4K3-900-SE

Step 6 — Transfer one listing dealer → dealer:

invoke transfer car900 not-your-fathers

Step 7 — Reprice two listings:

invoke reprice car900 13995
invoke reprice car103 15995

Step 8 — Transfer one listing to a buyer:

invoke transfer car900 buyer-alex

Step 9 — Remove one listing from inventory:

invoke delete car901

Step 10 — Verify all changes (run after each step if you want extra credit):

query all

6) Post New Listings (10–15 min)

A customer walks into Carmasté Used Cars and trades in a vehicle right as your manager says, “Let’s put it on the exchange immediately.”

Create a new listing using the invoke helper:

invoke create car900 silver 6 carmaste 14995

Optional: add vehicle details:

invoke set-vehicle car900 2019 Toyoda Coroll-Yeah SE 45888 WV-F4K3-900-SE

Re-run the inventory query:

query all

You should now see car900 in the output.

Why this matters: You’re writing new state to the ledger and observing how Fabric makes that change visible across participants.

Optional (do 1–2 more): Post one or two more listings with different mileage buckets and prices.

7) Run Dealership Workflows (20–30 min)

A) Wholesale swap between dealers (transfer)

Cascadia State University and Chesapeake Canoe University agree to transfer an asset between organizations.

Transfer control of the listing to Chesapeake Canoe University:

invoke transfer car900 not-your-fathers

Verify:

query car900

Watch the Logs, Blocks, and State terminals for the endorsement/commit activity.

Why this matters: Fabric enforces endorsement policies before commits. This is how multi-org trust is enforced without mining.

B) Price update (RepriceAsset)

The car sits for 20 minutes and suddenly “the market has spoken.” In Westview, that means someone checked a competing listing and panicked.

Use the dedicated function to update the price (same ID, updated AppraisedValue).

invoke reprice car900 13995

Then confirm:

query car900

Why this matters: State changes are explicit and auditable. In a shared exchange, this reduces disputes about when a price changed.

C) Final sale (transfer to buyer)

A buyer shows up with “a pre-approved loan” and the confidence of someone who watched one YouTube video about negotiation.

Transfer the listing to the buyer (any name is fine):

invoke transfer car900 buyer-alex

Verify:

query car900

D) Remove listing (DeleteAsset)

Once sold, the exchange should not keep advertising it as available inventory. Remove the listing:

invoke delete car900

Confirm it’s gone by querying all assets again:

query all

Why this matters: Real workflows include lifecycle events (listed → repriced → transferred → removed). Private ledgers can keep the history while presenting a clean current state.

8) Pricing & Paperwork (15–20 min)

These are dealership-friendly actions that track tags, title/inspection status, and “out-the-door” totals. Helper commands treat each argument as a single token, so use hyphens instead of spaces in short descriptions (e.g., Documentation-fee).

Step 1 — Add a tag that describes the listing:

invoke add-tag car103 certified-pre-owned

Step 2 — Set title and inspection status:

invoke set-title car103 clean
invoke set-inspection car103 passed

Step 3 — Add a paperwork fee:

invoke add-fee car103 DOC Documentation-fee 199

Step 4 — Add an optional addon:

invoke add-addon car103 TINT Window-tint 350

Step 5 — Set dealer pricing config:

invoke set-dealer-pricing carmaste DEALER_MARKUP Dealer-adjustment 500 625

Step 6 — Apply that dealer markup to the listing:

invoke apply-dealer-markup car103 carmaste

Step 7 — Compute the out-the-door price breakdown:

query price car103

Step 8 — Optional cleanup:

invoke remove-tag car103 certified-pre-owned
invoke remove-fee car103 DOC

9) Under the Hood: peer CLI (optional)

The invoke and query helpers are convenience wrappers around the Fabric CLI. Under the hood, they run peer commands with the right channel (-C), chaincode name (-n), and JSON payload (-c).

The peer command does much more than chaincode operations. Here is the built‑in help menu (spacing normalized so it renders cleanly in terminals):

$ peer -h
Using organization 1
Usage:
  peer [command]

Available Commands:
  chaincode   Operate a chaincode: install|instantiate|invoke|package|query|signpackage|upgrade|list
  channel     Operate a channel: create|fetch|join|joinbysnapshot|joinbysnapshotstatus|list|update|signconfigtx|getinfo
  completion  Generate the autocompletion script for the specified shell
  help        Help about any command
  lifecycle   Perform _lifecycle operations
  node        Operate a peer node: start|reset|rollback|pause|resume|rebuild-dbs|unjoin|upgrade-dbs
  snapshot    Manage snapshot requests: submitrequest|cancelrequest|listpending
  version     Print fabric peer version

Flags:
  -h, --help  help for peer

Use "peer [command] --help" for more information about a command.

What these options do:

  • chaincode — install, invoke, query, and manage chaincode on peers
  • channel — create/join channels and fetch channel data or config
  • lifecycle — manage chaincode definitions (the modern deployment path)
  • node — operate the peer node process and its databases
  • snapshot — manage state snapshots for data portability
  • completion — generate shell auto‑complete scripts
  • version — print peer binary version info
  • help and -h/--help — discover usage details

Tip: if your terminal shows tabbed spacing, run peer -h | expand -t 2 to convert tabs to spaces.

Chaincode syntax basics:

  • Invoke (write): peer chaincode invoke -C <channel> -n <chaincode> -c '{"Args":["Function","arg1","arg2"]}'
  • Query (read): peer chaincode query -C <channel> -n <chaincode> -c '{"Args":["Function","arg1"]}'

Replay a few earlier steps using the peer CLI:

  1. Init the ledger:
peer chaincode invoke -C mychannel -n basic -c '{"Args":["InitLedger"]}'
  1. Create a listing:
peer chaincode invoke -C mychannel -n basic -c '{"Args":["CreateAsset","car902","gray","7","carmaste","13995"]}'
  1. Set vehicle details:
peer chaincode invoke -C mychannel -n basic -c '{"Args":["SetVehicleDetails","car902","2018","SubaRoo","Outbackpack","Premium","72000","WV-F4K3-902-PR"]}'
  1. Read it back:
peer chaincode query -C mychannel -n basic -c '{"Args":["ReadAsset","car902"]}'

Why This Lab Matters

You just operated a permissioned blockchain network and watched it behave like a real enterprise system:

  • Identity + MSP replaces anonymous participation
  • Endorsement replaces proof-of-work
  • Ordering guarantees consistency without mining
  • Channels provide privacy and governance
  • Shared state + history reduces multi-party disputes (who changed what, when)

This gives you a practical foundation before you move deeper into smart contract security and adversarial blockchain behavior.
