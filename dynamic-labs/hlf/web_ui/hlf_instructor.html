How to Run a Class

Quick operational runbook for the Phase 7 classroom flow. The Classroom panel above is the single control surface for everything described here.

  • Before class. Start the network (Start Network above). Set Pool Size to ~20% of expected class size (e.g. 4 for a class of 20) so the first wave of students gets hot peers with no boot wait. Set Policy to wipe for the first class (guarantees a clean slate on reuse); switch to sticky if you want students' work to survive brief disconnects. Distribute the claim URL to students: /labs/hlf/claim. Each student gets their own UUID cookie, their own lane (s01…sNN), their own peer, and their own ttyd shell.
  • During class. Watch the lane grid: green = running, amber = starting/stopping, red = error, grey = stopped. Each cell shows the claim's UUID prefix (or "unclaimed") and idle time. Nudge a stuck student: Reset their lane to rebuild their peer (their state goes, but the shared ledger is untouched). Demo a fault: use the scenario panel — Cascadia/Chesapeake Canoe/South Hudson/Maple Leaf peer outage, orderer outage, endorsement policy failure. These hit the 4 consortium peers and the orderer, not any student peer. Pause the sweeper during an exam so nobody gets auto-released for going quiet.
  • End of class. Switch Policy to wipe if not already. Click Release on every claimed lane (or just run the idle sweeper — it'll get them). For a hard reset between classes, use Reset Network at the top — rebuilds everything from genesis, including the shared ledger. The per-lane Reset only wipes one student's peer.
  • If something breaks. Check Recent Network Logs below for orderer/peer errors. A lane stuck in error usually means docker-compose couldn't start the peer — try per-lane Reset, then Start. A lane stuck in starting > 30s likely means the peer is replaying the ledger — give it another minute before assuming it's broken.

Infrastructure Notes

The classroom runs one real Hyperledger Fabric consortium — one orderer, four always-on org peers (Cascadia State, Chesapeake Canoe University, South Hudson, Maple Leaf) under 3-of-4 MAJORITY endorsement — plus one on-demand peer per student, all joined to the same channel and writing to the same shared ledger. Every chain operation (block fetch, chaincode invoke, fault injection) goes through genuine Fabric tooling (peer, configtxlator, docker). The notes below call out where the UI takes small liberties with presentation, and (at the bottom) what is genuinely live.

Classroom Topology

  • Lane manager. Runs inside hlf-runner. Owns the configured student lanes (s01…sNN), each mapped to a profile-gated peer service in compose-students.yaml. It brings peers up on demand — each peer container runs its own built-in ttyd (baked into the hlf-peer-ttyd image), tied to that student's admin MSP — and stops idle peers to free RAM. Lane state persists in runtime/lanes.json so restarts don't drop the world.
  • Claim manager. Sits in front of the lane manager. Each student calls GET /labs/hlf/claim and gets a UUID cookie + a station (lowest-numbered free s##). Resuming from the same device reuses the same UUID. An idle sweeper releases claims after a timeout; pause it during exams. Release policy decides whether the peer survives (sticky) or is wiped back to pool-clean (wipe).
  • Hot-swap pool. Pool Size is how many unclaimed peers to keep pre-warmed. When a student claims, the lowest warm peer is handed over and the pool refills in the background. Shrinking the pool stops the surplus peers; growing it boots new ones async. Hot Free is the instantaneous pool depth.
  • Endorsement on student writes. Every student write needs the student's own peer to endorse, plus the matching consortium peer for their org identity — so writes go through two real Fabric signatures even in the single-student case. With all four consortium peers up, the 3-of-4 MAJORITY policy still applies to the consortium side.
  • Per-student reset ≠ network reset. The Reset button on a lane tears down one student's peer + volume only. Crypto, channel membership, and ledger all persist; the peer will resync from the orderer when it comes back. The Reset Network button at the top tears down everything and regenerates from genesis — use that only between classes.

Presentation Caveats

  • Chaincode source viewer. Explorer → Chaincode → View Source reads the chaincode files from disk (runtime/fabric-samples/asset-transfer-basic/chaincode-javascript/), not from the installed tarball on the peer. The committed Package ID hash shown above it is computed from the tarball that was actually installed, so the two should match — but if someone edits the disk source after install, the modal will show the edited source while the chain keeps running the original.
  • Governance panel is cached ~15s. Channel policy comes from a real peer channel fetch config + configtxlator proto_decode, but the result is cached for up to 15 seconds to keep the UI snappy. After a policy change (rare in this lab), the panel can lag briefly.
  • Block type labels. The integer type field from the block header is mapped to readable labels (ENDORSER_TRANSACTION, CONFIG, etc.) in Python. The integers themselves are real and come straight from the decoded protobuf — the mapping is just for display.
  • Endorser identities. Transaction detail shows a certificate fingerprint + CN/OU extracted from the endorser's PEM. The PEM bytes are real (pulled from the block); the fingerprint is a SHA-256 digest we compute for readability.
